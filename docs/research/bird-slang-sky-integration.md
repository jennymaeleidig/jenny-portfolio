# Turning bird.slang into a sky-integrated flock pass

> **Retired, 2026-11-23.** `assets/shaders/bird.slang` and both prototype
> branches (`prototype/bird-flock`, `prototype/bird-sky-migration`) were
> retired after the flock was folded into the sky. This note is the surviving
> record; its file and line references describe the now-deleted prototype,
> not shipped code.

Research question: what does `assets/shaders/bird.slang` actually do today, what conventions does the site's sky already establish that a flock pass must obey (ramp, dither, cells, stars, levers, light/dark gating), and what does the official Slang playground offer beyond `[playground::SLIDER]` for tuning and per-bird randomization?

Date: 2026-11-23. All repo claims verified against the repo's own code with line numbers. Slang playground claims verified against the playground's own compiler source and user-facing documentation (the `shader-slang/slang-playground` repository, pinned at commit `631c0d8`), which are the primary sources for the attribute set; `docs.shader-slang.com` was unreachable from this machine (fetch failures on every path), so the official playground docs shipped inside the playground repo — `engine/slang-compilation-engine/media/playgroundDocumentation.md` — stand in as the primary documentation.

## What bird.slang does today

`assets/shaders/bird.slang` (135 lines) is a single-bird WebGPU compute shader written for the Slang playground, already deliberately aligned with the sky's look:

- **Entrypoint**: `[shader("compute")]`, `[numthreads(16, 16, 1)]`, `[playground::CALL::SIZE_OF("outputTexture")]` on `void imageMain(uint3 dispatchThreadID: SV_DispatchThreadID)` (lines 66-69). It imports `playground` and `rendering` (lines 1-2), gets `outputTexture.GetDimensions(width, height)` (line 75), stores an opaque `float4` per pixel (line 134), and early-returns outside the dispatch bounds (lines 78-80). It overwrites the whole output — there is no sky underneath; the background is a hardcoded ramp colour (line 126).
- **Playground uniforms**: `[playground::TIME]` (ms, line 5) and `[playground::FRAME_ID]` (line 9); the animation clock is `max(timeMs / 1000.0, frameId / 60.0)` so it moves when the host leaves TIME at zero (line 85). Nine `[playground::SLIDER(default, min, max)]` tunables (lines 12-51): `thickness` (perpendicular wing half-width), `zoom` (world units spanning canvas height), `offsetX`/`offsetY` (bird position in world units), `wingCutoff` (x extent of wings), `flapSpeed` (Hz), `dither` (edge dither share, default 0.2 = the sky's shipped 20%), `bobAmp`, `bobSpeed`, and `blockPx` (output px per block; 0 derives it from the band width).
- **Wing shape**: `wingY(x, droop) = 1.5 * sqrt(abs(x * 0.5)) - droop * x²` — a fixed sqrt middle with an x² droop coefficient lerping between 0.5 (wingtips swept down) and 0.0 (flat glide) (lines 55-57). `wingDx` is the slope, clamped near the x=0 cusp where the true derivative is infinite (lines 61-64).
- **Flap**: `flap = 0.5 + 0.5 * sin(birdTime * flapSpeed * 2π)`, then quantised to 4 held levels (`flapSteps = 4`, "sky-twinkle rhythm", lines 71, 86-89) so blocks do not crawl every frame; `droop = lerp(0.5, 0.0, flap)` (line 90).
- **Bob**: `bob = bobAmp * sin(birdTime * bobSpeed * 2π)` applied as `p.y += bob` (lines 91, 107). Today bob is an independent sine — **not** inversely synced to flap, and `bobAmp` is a free slider, not derived from `wingCutoff`. The rewrite's spec (wing down → body bobs up; bob amplitude derived from wingCutoff) is a change, not a restoration.
- **Mosaic**: `BLOCK = max(1, round(thickness * height / zoom * 0.5))`, overridden by `blockPx >= 1` (lines 93-96); cell = `dispatchThreadID.xy / BLOCK` (line 97); a 3×3 sample grid at 1/6, 3/6, 5/6 across each cell counts hits against `abs(p.y - wingY(p.x, droop)) < thickness * sqrt(1 + slope²)` (slope-corrected constant perpendicular width) within `abs(p.x) <= wingCutoff` (lines 100-113).
- **Dither**: coverage = hits/9; `lineMask = step(0.5, coverage + dither * BAYER4[(cell.y % 4) * 4 + cell.x % 4])`, using a literal copy of the sky's 4×4 Bayer matrix (lines 40-46, 116-119).
- **Colour**: hardcoded sky-ramp literals — background `#DFE5E7` (ramp index 0), bird `#2157CC` (ramp index 3), lerped by lineMask (lines 122-129). A flock pass would instead need per-block compositing against the actual sky frame.

## Sky conventions a bird layer must follow

From `assets/sky-core.mjs` (852 lines) and `assets/sky.js` (261 lines):

- **Ramps**: `RAMP` (light, `sky-core.mjs` lines 23-32): `#DFE5E7` (index 0, lightest/clear), `#C5D5E5` (1), `#9EC8E4` (2), `#2157CC` (3, darkest/blue). `DARK_RAMP` (lines 35-42): `#C0BBAC`, `#777578`, `#414042`, `#1B1A16`. `rampAt(mix)` interpolates them (lines 87-92); `rampIndex(band, tones)` maps a band index to a ramp index, lightest first (lines 662-666).
- **Dither**: `BAYER4` (lines 227-243), 4×4 offsets in 1/32 units below zero, indexed `BAYER4[(y & 3) * 4 + (x & 3)]` per block (line 766). Tone bands are quantised with `toneIndex(value, thresholds, dither, bayer)` clamped to one band either side (lines 628-645); `dither` is a percent (SKY_DEFAULTS ships 20, lines 141/160).
- **Cells/blocks**: `SKY_DEFAULTS.cell = 2` CSS px (line 146); `frameLayout` snaps a cell to whole device px: `round(cell * dpr) / dpr`, then cols/rows cover the frame (lines 277-296). `renderFrame` writes one RGBA pixel per block into `Uint8ClampedArray(cols * rows * 4)` (lines 688+). OFFSET_Y_LIMIT = 400 CSS px (line 273).
- **SKY_DEFAULTS** (lines 136-170): `mode: "frame"`, plus numeric knobs including `seed: 12`, `maxFps: 60`, and the ten `star*` knobs. A visit randomises only `seed` (`sky.js` line 26).
- **Stars — the closest prior art for a bird layer** (`createStarLayer`, lines 328-459; twinkle 461-530): stars live on a jittered grid in block coordinates anchored at the viewport origin, so a resize reveals new cells instead of moving or reseeding visible ones (lines 330-334). Per-star randomisation is drawn from the shared `hash(x, y, seed + offset, period)` (lines 320-322, 352-367) — offsets 0-8 decide presence, position, size (1 block / 2-block pair / 5-block plus with dim corners), tint, phase, variance, direction. Twinkle is three incommensurate sines quantised to three held levels with a 0.25s hold and deadband (lines 461-530). **Crucially, persistence is baked in the data model**: `peak`, `tint`, `owner` are typed arrays over the whole frame, `stars` carries per-star mutable state (`phase, size, gain, level, nextChange`), built once per layout/seed — not recomputed per frame. A bird layer spawning off-screen right and drifting left needs the same shape: per-bird state (spawn x, y, speed, phase, size) created once, positions derived from `time` each frame.
- **Compositing**: `renderFrame` (lines 688-777) computes the ramp colour per block, then stars paint only in the clear band (`band === 0`, line 748), each star block lerped over the band's own colour by the mix (`lerpColour(clearColour, starColour, blend)`, line 765). This is the template for compositing birds over whichever band they cross: read the sky's block colour first, then overwrite or blend bird blocks on top. A bird crossing tone bands should probably pick its own colour by band or read the underlying block.
- **Theme crossing**: `TRANSITION_MS = TURN_MS` (lines 47-51); `mix` crosses ramps with the star layer fading in over the same mix (`stars = blend > 0 && starLayer ? starLayer : null`, line 730; test "stars fade in with the ramp", tests/sky.test.mjs line 906). In `sky.js`, `mix` starts at `dark ? 1 : 0` (line 53), `themechange` flights it with `transitionMix` (lines 218-248), and `isDark` comes from `theme-core.mjs`'s two-state test `value === DARK` on `<html data-theme>` (theme-core.mjs lines 15-23). **Light-mode-only mechanically** means the bird layer is the mirror of stars: render birds only when `blend === 0` (or fade them out as `blend` rises, lerping toward the underlying sky colour like stars do in reverse); a mid-crossing frame would show birds dissolving with the same dither. `sky.js` also has the "wash"/"off" modes and reduced-motion handling (`settle`, lines 190-196) that a bird pass must respect — reduced motion should presumably freeze birds, as it freezes stars' twinkle.

### Levers panel

`assets/sky-levers.mjs` (700 lines), gated by the build:

- **Slider spec shape**: `{ key, label, min, max, step, rebuild?, mul?, life?, group?, hint }` (lines 13-236). `rebuild: true` calls `controller.rebuild()` (resize) instead of `redraw()` (draw) (lines 504-511); `mul` scales the slider's raw range into config units (`gain` uses `mul: 0.01`); `life: true` slots a slider under the "life" heading; `group: "stars"` slots it under the "stars" heading. **One panel, headed sections** — `sky` (no life/group), `life`, `stars` (lines 426-428) — so a "birds" section would be a fourth `<h4>birds</h4>` group with `group: "birds"` sliders, not a second panel.
- **Publication**: `assets/sky.js` publishes `globalThis.skyLevers = { config, redraw, rebuild, restart }` only when `<body data-sky-levers>` is present (sky.js lines 241-250); `sky-levers.mjs` reads `globalThis.skyLevers` at import (line 12) and does nothing without it. **Bird config should ride the same `config` object** (or the panel needs a second controller; the cheap path is `bird*` keys on the same config).
- **Copy values**: `copyValues` prints `mode`, every slider key via `format(slider, position(slider))`, and `maxFps` as a `SKY_DEFAULTS`-shaped paste block (lines 556-577) — new bird keys automatically appear if added to `sliders` and `SKY_DEFAULTS`. `seed` is deliberately excluded (comment, lines 549-552).
- **Gating**: `scripts/post-build.sh` lines 68-72 `rm -f "$DIST/assets/sky-levers.mjs"` unless `SKY_LEVERS=1`; `layouts/shell.sh` `sky_levers_attr()` (lines 142-147) stamps `data-sky-levers` on `<body>`, and `page_close` (lines 221-223) emits the `<script src="/assets/sky-levers.mjs">` tag only under the flag. A production tree has neither module nor attribute.

### Test convention

`tests/sky.test.mjs` (1015 lines, `node:test` + `assert/strict`): pure-function tests over `sky-core.mjs` exports at fixed `fieldOptions` (cols 24, rows 12, cellPx 2, seed 12, lines 28-34). Representative patterns a bird layer would follow: "the star layer is deterministic for a seed" / "a different seed gives a different star layer" (lines 625-643), share knob behaviour ("star density turns the layer off and fills every cell", line 645), band placement ("stars paint only in the dark clear band", line 718), and mix gating ("stars fade in with the ramp and land on the shipped tints", line 906). So: a bird layer earns tests for determinism per seed, spawn/drift geometry, light-mode gating (`mix === 0`), and flap/bob inverse sync.

## Slang playground attribute capabilities (primary sources)

Verified against `shader-slang/slang-playground` at commit `631c0d838fef1e7992e2a71a91c71ef89cb84f10`:

- **Uniform controllers** (compiler source `engine/slang-compilation-engine/src/playgroundCompiler.ts`, `UNIFORM_PARSERS`, and shared type `UniformController` in `engine/shared/src/playgroundInterface.ts`): `SLIDER(default, min, max)` — 32-bit float scalars only; `COLOR_PICK(r, g, b)` — float3 colour picker; `TIME` — ms clock; `FRAME_ID` — frame index; `MOUSE_POSITION` — float4 mouse; `KEY("KeyA")` — scalar 1/0 key state. **That is the complete list**: there is no toggle, no section/group attribute, and no SEED attribute in the playground's uniform vocabulary.
- **Resource commands** (same file, `getParsedCommandsFromAttributes`; user-facing docs `engine/slang-compilation-engine/media/playgroundDocumentation.md`): `ZEROS(n)`, `RAND(n)` — "Initialize a `float` buffer with uniform random floats between 0 and 1" (structured buffers only), `BLACK(w,h)`, `BLACK_3D`, `BLACK_SCREEN(sx,sy)`, `URL("...")`, `DATA(url)`, `SAMPLER`.
- **Dispatch commands** on entrypoints: `CALL(w,h,d)`, `CALL::SIZE_OF("resource")`, `CALL_INDIRECT("buffer", offset)`, `CALL::ONCE` (docs: "Only dispatch the compute pass once at the start of rendering. Should be used in addition to another CALL command").
- **Implications for the flock**: `[playground::RAND(8 * K)]` is the official per-bird randomization route — fill a `StructuredBuffer<float>` (or a `ParameterBlock`-typed struct buffer via `DATA` is not needed since RAND is float-only) and read K floats per bird; combined with `CALL::ONCE` a one-time init pass could scatter them into a persistent buffer. But RAND has no seed control — the values are fresh per run — so if the site wants per-visit determinism like the sky's `seed`, the site-side integration should pass a seed uniform (a plain `[playground::SLIDER]` or an ordinary uniform) and derive per-bird params from a hash in-shader, mirroring `hash(x, y, seed)` in sky-core. Grouping a "birds" panel is not a playground capability; the levers panel is the site's own grouping mechanism.

Note: `docs.shader-slang.com` itself (TIME/FRAME_ID/SLIDER semantics) could not be fetched from this machine; the playground repo's own compiler and documentation, cited above, are the authoritative sources for the playground attribute set.

## Open questions the grilling should settle

1. **Bird count and spacing**: how many birds, and are they a jittered lane grid (star-style) or Poisson-ish scattered rows? Star density precedent suggests a percent knob, but birds read as a flock, not a texture.
2. **Spawn/drift mechanics**: fixed spawn x just off-screen right with per-bird speed, or a star-style periodic wrap? Does drift speed tie to `config.speed` (the clouds' 20 CSS px/s) or get its own knob? Do birds wrap (re-spawn right) or land and stop?
3. **Light-mode gating during a crossing**: hard off at `mix > 0` (stars' mirror: stars are null at blend 0, birds null at blend > 0), or fade out over the crossing's TRANSITION_MS like stars fade in? And what settles under reduced motion — birds frozen mid-flight or removed?
4. **Colour per band**: is the bird always `#2157CC` (ramp 3) regardless of the band it crosses, or does it read the underlying block colour and pick a contrasting ramp index? bird.slang today paints bg ramp-0 + bird ramp-3 regardless of position.
5. **Flap/bob sync law**: "wing down → body bobs up" and "bob amplitude derived from wingCutoff" still leave the phase law open — bob = −(wing droop)? And is the bob applied to the world-space bird position (per-bird) or to the sampling offset as today?
6. **Render path**: does the flock port bird.slang into the sky's CPU `renderFrame` (pixel-art consistency, tests, no WebGPU dependency — the site currently has **no** WebGPU usage; bird.slang is a playground artifact), or does a WebGPU canvas layer get introduced? The star layer's precedent argues strongly for `sky-core.mjs` pure functions; the Slang file then becomes design source, not shipped code.
7. **Which knobs get levers**: bird count, speed, flap speed, size, dither share — which are SKY_DEFAULTS entries with `group: "birds"` sliders, and which stay hardcoded? Does `copyValues` include them (they will, automatically, if in `sliders`)?
8. **Seed**: per-visit random seed like the sky's, or the SKY_DEFAULTS seed for a fixed flock? RAND's unseeded nature makes a site-side `hash`-based derivation the deterministic option.
9. **Mode interaction**: do birds hide in "wash" and "off" modes along with the canvas, or does "off" still show birds (it is a sky canvas, so presumably birds live and die with it)?
