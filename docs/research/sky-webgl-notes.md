# The sky's WebGL2 crossing: per-frame contract, wing stamps, shader layout, and headless testing

Research question: what exactly must the planned WebGL2 fragment kernel receive per frame, how should the flock's CPU wing silhouettes be cached, how should the shader source and context be laid out, and how can the adapter be tested headless against the pure core — verified against primary sources rather than assumed? This note feeds issue #66 under ADR-0007.

Date: 2026-11-23. All claims are verified against primary sources (Khronos registry specification PDFs fetched and text-extracted, the WebGL 2.0 spec, MDN, vendor docs, project READMEs via the GitHub API), fetched directly. Where a source does not answer something, that is stated rather than inferred, and the gap is filled by reasoning-from-the-repo, labelled as such.

## 1. The per-frame data contract for the fragment kernel

### 1a. Packing a 16-bit value into two RG8 channels

The OpenGL ES Shading Language 3.00 (Khronos registry, `GLSL_ES_Specification_3.00.pdf`, §4.5) states that "all integral types are assumed to be implemented as integers and so may not be emulated by floating point values", and the language has full bitwise operators (§5). GLSL ES 3.00 therefore does not need the pre-integer-era float packing trickery: the correct idiom is to upload the two bytes as `gl.RG8`/`gl.UNSIGNED_BYTE` and unpack with integer ops after a `texelFetch`:

```glsl
precision highp float;               // §4.5.4: the fragment language has NO
                                     // default float precision; declare one.
...
uvec2 b = uvec2(texelFetch(uField, p, 0).rg * 255.0 + 0.5);
uint v = (b.x << 8) | b.y;           // 0..65535
float value = float(v) / 65535.0;
```

The `* 255.0 + 0.5` rounding matters: UNORM texels are returned normalised (k/255), and the older float-only packing literature documents that skipping the round loses random bits — the "16-Bit Color Encoding on the GPU" write-up (theinstructionlimit.com) found it had to add `round` "for reasons unknown… I keep losing random bits". In highp the round is exact.

Precision pitfalls, from the spec's own range table (§4.5.1, fetched):

- `mediump` float is only guaranteed a range of (−2^14, 2^14) and a relative precision of 2^-10 — about 1,024 distinguishable relative levels, which cannot carry a 16-bit field value, and cannot even hold the intermediate `255 × 256 = 65280` of a naive unpack. Do the unpack in `highp`.
- `highp` is IEEE-754 single precision (relative 2^-24) — ample.
- GLSL ES 3.00 contains no clause making fragment `highp` optional. That clause exists only in GLSL ES 1.00 (the version webglfundamentals.org quotes, fetched: "Support for `highp` is optional"); the 3.00 spec text was searched and has no such provision, and its §4.5.4 requires an explicit float precision declaration in the fragment language — `precision highp float;` at the top of the kernel is both mandatory-in-form and correct-in-substance. No source states that every shipping ES 3.0 device implements fragment highp in hardware; but WebGL2 requires the ES 3.0 conformance profile, so a `highp`-declaring shader is within the contract the adapter already commits to by requesting the context.

One pitfall the format itself creates, marked here as reasoning-from-the-format (no fetched source states it outright): `LINEAR` texture filtering interpolates each channel independently in normalised space, so a hardware-lerped RG8 pair is not the lerp of the 16-bit value (the low byte crosses its 255→0 rollover while the high byte is unchanged, and the weighted sum of `hi/255` values is not the weighted sum of values). And the core's own interpolation is not plain bilinear: `renderFrame` (assets/sky-core.mjs, around line 930) lerps between two manually wrapped columns `a`/`b` and two rows `skyRow`/`skyNext` with its own fraction terms, plus the warp's per-row `sampleOffset`. The kernel should therefore not rely on the sampler's filtering at all: set NEAREST/CLAMP on the field textures, `texelFetch` the four relevant texels, and reproduce the core's lerp arithmetic in-shader. This also sidesteps any question of whether filtered-UNORM rounding matches the CPU.

### 1b. Wrap, filter, and NPOT

The WebGL 2.0 specification (registry.khronos.org/webgl/specs/latest/2.0/, fetched) settles the NPOT question explicitly, under "Non-Power-of-Two Texture Access": "Texture access works in the WebGL 2.0 API as in the OpenGL ES 3.0 API. In other words, unlike the WebGL 1.0 API, there are no special restrictions on non power of 2 textures. All mipmapping and all wrapping modes are supported for non-power-of-two images." The OpenGL ES 3.0.6 spec's texture-completeness rules (§3.8.13, fetched and searched) likewise contain no power-of-two condition — the field can be REPEAT-wrapped at its natural width (one period, `cols + 2·GUTTER + 2`, never a power of two) with no padding. The MDN tutorial's NPOT restrictions (developer.mozilla.org, "Using textures in WebGL", fetched) are explicitly WebGL 1 rules and do not apply.

Recommendation, blending the spec answer with the repo's own sampling (reasoning-from-the-repo): since the core wraps x by hand (`wrap(offset, width)`, column `a`/`b` arithmetic) and clamps y against the margin, the cleanest contract is REPEAT wrap on S (harmless, and correct if the sampler's wrap is ever used), CLAMP_TO_EDGE on T, NEAREST filtering — the wrap and lerp happen in the kernel's own math, matching `renderFrame` exactly. A single mip level (`texStorage2D` with one level) is all the field needs; MDN's WebGL best practices (fetched) recommends `texStorage` over `texImage` for exactly this single-level case, because some drivers allocate an entire mip chain behind `texImage`.

### 1c. Precision declarations and CPU-side wrapping of time/offset

From the GLSL ES 3.00 spec (§4.5.1, fetched): fragment `highp` is IEEE-754 single precision; `mediump` is only guaranteed (−2^14, 2^14) with 2^-10 relative precision. webglfundamentals.org (fetched, secondary) confirms the practical reading: on desktop GPUs all qualifiers run as highp anyway, and on mobile `mediump` is a real, lower precision that visibly breaks shaders that assumed more. The kernel's field values, thresholds and dither math live comfortably in highp; nothing in the per-frame pass needs more than [0,1] plus small offsets.

What must be wrapped on the CPU, reasoning-from-the-repo against `renderFrame` and `updateStarGains` (assets/sky-core.mjs):

- `offset` already enters wrapped (`wrap(offset, width)`), and the spec's float range is irrelevant to the value itself — but the CPU's `elapsed`/`offset` accumulators grow without bound across a long visit, so the wrapping must happen before the uniform upload, not after. ADR-0007 already mandates this ("monotonic clocks are wrapped into small ranges on the CPU before they become uniforms").
- `time` feeds four oscillators: the warp sine (`y·0.055 + time·warpSpeed`, period 2π/warpSpeed), the twinkle's three sines (periods 7.3/speed, 3.1/speed, 11.7/speed — incommensurate by design), and each bird's flap beat (`time·flapHz·variance + phase`, period 1/(flapHz·variance)). The safe CPU-side wrap is per-oscillator: upload each oscillator's phase already reduced into [0, one period) — the sines and the flap are all periodic, so reducing each phase mod its period on the CPU is exact in the mathematical sense, and each reduced value stays well inside even mediump's (−2^14, 2^14) guaranteed range. The star gains and bird droop depend on these phases only, so no information is lost. The WebGL spec itself guarantees nothing about large-float uniform accuracy beyond highp's IEEE-754 definition (§4.5.1, fetched); the wrap is insurance against long sessions, and the phases are the right wrap points because they are the only places time enters the maths.

### 1d. Uniform and texture-unit budgets

From the GLSL ES 3.00 spec's built-in constants (§7.3, fetched verbatim — "the actual values used are implementation dependent, but must be at least the value shown"):

```
const mediump int gl_MaxFragmentUniformVectors   = 224;
const mediump int gl_MaxTextureImageUnits        = 16;
const mediump int gl_MaxCombinedTextureImageUnits = 32;
```

- The flock at ~30 birds × 8 floats is 240 floats = 60 vec4s — well inside the guaranteed minimum of 224 fragment uniform vectors (and inside it even doubled, if the flock grows). No feature detection or splitting is needed. (An aside from the same spec section: `gl_MaxFragmentInputVectors = 15`, irrelevant here since the kernel has one fullscreen triangle and no varyings beyond position.)
- Field + evolution field + star layout = 3 texture units, against a guaranteed 16 fragment units / 32 combined. The star layout could even absorb the flock's per-bird uniforms as a texture later without approaching any limit.

## 2. Stamp-cache keying for the flock's CPU path

External sources are thin here, and that is stated plainly: no primary source governs caching of procedurally generated pixel sprites in a raw pixel buffer. The closest primary guidance is MDN's "Optimizing canvas" (developer.mozilla.org, fetched): "Pre-render similar primitives or repeating objects on an offscreen canvas… render the offscreen image to your primary canvas as often as needed, without unnecessarily repeating the steps needed to generate it in the first place", plus its rules to use integer coordinates and not to scale in `drawImage`. That guidance is written for the 2D context; the sky does not paint into one. Reasoning-from-the-repo takes over:

- `paintBirds` (assets/sky-core.mjs, around line 1100) composes into the same `Uint8ClampedArray` that becomes `ImageData` — there is no 2D context anywhere in the render path (`assets/sky.js` creates one only to `putImageData`). So an offscreen canvas is the wrong store: it would force a per-bird `getImageData` or a full-context switch. The right store is a raw typed array per stamp, holding per-block coverage, composed by the same buffer arithmetic the flock already uses.
- The dither forbids a pure alpha mask. A block is inked when `hits/denom + dither·bayer < 0.5` fails, and the Bayer term depends on the block's position mod 4 (`BAYER4[(y & 3)·4 + (x & 3)]`), which varies as the bird drifts. So the stamp cannot bake the threshold decision; it must bake the coverage (`hits/denom`, one byte per block) and leave the `+ dither·bayer < 0.5` test and the `lerpColour` ink blend to the blit, where they are a few adds per block. With that split, the blit is exact, not approximate: whole-block snapping (`birdSnap`) makes `bx`/`by` integers, and coverage for a block depends only on `(x − bx, y − by)`, which translation by whole blocks preserves.
- Keying: per (bird, flap step). The wing shape is not shared across birds — `wing` is rolled per bird (`wingBase·(1 + (scaleRoll − 0.5)·2·scaleJitter)` in `createBirdLayer`) and is generally not an integer (`params.scale / cellPx`, e.g. 31/4), so a unit-wing stamp blitted with integer scaling does not reproduce the per-bird silhouette, and wing-size normalisation would quantise sizes the flock deliberately rolls. The silhouette for a given bird depends only on its `wing`, its layer's shaping params (fixed per rebuild) and the flap step (droop is a function of the quantised `flap`), so (bird, flap step) is the exact key. `flapSteps` is 2–8 by config, so the cache is ~30 × 8 coverage grids of roughly `(2·wing + 2)²` bytes each — on the order of 100–200 KB worst case, trivial against the field's own buffers.
- Rebuild invalidation: the key ingredients (wing rolls, layer params, flap steps) are all chosen in `createBirdLayer`, so the cache is built there, once per rebuild/reseed, exactly as the spec's "baked once per rebuild" wording requires. The `birdBands` occlusion check for the back layer stays at blit time, since it depends on the frame's tone bands.

## 3. Shader source layout and context creation

- **Inline vs fetched source**: no fetched source answers this directly — MDN's WebGL best practices (fetched) discusses shader _compilation_ timing at length but says nothing about how the source string reaches `gl.shaderSource`. MDN's own tutorials embed shaders in the document; that is convention, not a rule. Reasoning-from-the-repo: the sky is one ES module with no build step (`assets/sky.js` imports `sky-core.mjs` directly), and a runtime `fetch` of a `.glsl` file would add a new failure mode to a script whose header promises the page works when it fails to load. Inline the two shaders (a handful of lines of vertex source plus the kernel) as template literals in the module. This also keeps the poster path and the no-JS path untouched.
- **Compilation timing**: from MDN best practices (fetched): compile shaders and link programs in parallel rather than serially; prefer `KHR_parallel_shader_compile` when present; and "don't check shader compile status unless linking fails" — the ESSL3 error-handling rules it quotes guarantee all lexical/semantic errors surface at `glLinkProgram`, so a single `LINK_STATUS` check with both info-logs is the correct, least-blocking pattern for a one-program adapter. The adapter is chosen once per load, so this runs once, not per frame.
- **Context loss**: the WebGL 2.0 spec (fetched) defines a per-context "webgl context lost flag"; MDN documents the `webglcontextlost`/`webglcontextrestored` events (spec §5.15.2 cited on the event page, fetched) and MDN best practices says to "handle webglcontextlost events, which can be emitted when the GPU runs out of memory, among other reasons". Reasoning-from-the-repo for the response: on `webglcontextlost`, call `event.preventDefault()` and run the existing `stop()`; on `webglcontextrestored`, run the existing `resize()` path — it rebuilds the scene from seed and re-uploads every static texture, which is exactly the recovery a context restore needs, and the sky's seeds survive because they live outside the adapter. No source specifies the restore procedure beyond the spec's flag semantics; the resize-path answer is the repo's own, and it fits.
- **Context attributes**: from MDN `getContext` (fetched) for the vocabulary, MDN best practices for the judgement calls:
  - `antialias: false`, `depth: false`, `stencil: false` — none are wanted; MDN best practices notes depth/stencil formats are inseparable and costly on some devices ("only request a stencil buffer… if you use it").
  - `alpha`: MDN best practices warns `alpha: false` "can be expensive" on some platforms and recommends instead structuring the shader to write `1.0` alpha — which the kernel does trivially, since every fragment is painted. Keep the default `alpha: true` and write opaque output.
  - `preserveDrawingBuffer: false` (the default) — the kernel repaints every fragment each frame; nothing is read back.
  - `powerPreference: "low-power"` — MDN lists it; a decorative background sky is its textbook case. No fetched source mandates it for backgrounds; it is a hint, and the sky's 24 fps cap is the real power lever.
  - `desynchronized`: MDN `getContext` documents it as a latency hint; the Chrome low-latency post (developer.chrome.com, fetched) confirms it applies to `webgl2` but requires `preserveDrawingBuffer: true` to avoid flicker ("Some browsers including Chrome clear WebGL canvases between frames… causing the image being drawn to flicker") and may tear. For a 24 fps background, skip it — the flicker workaround reintroduces exactly the buffer preservation the adapter avoids, and nothing in the spec of the sky needs sub-frame latency.
- **Backing store smaller than CSS size**: confirmed by MDN best practices verbatim (fetched): "Consider rendering to a smaller back buffer… reducing canvas.width and height and keeping canvas.style.width and height at a constant size." The browser scales the backing store to the CSS box; `image-rendering: pixelated` keeps the scaling nearest-neighbour. Reasoning-from-the-repo: the CPU path already does this (`canvas.width = layout.cols`, `canvas.style.width = cols·cellPx` in `assets/sky.js`), so the GL path simply inherits the identical canvas sizing — one fragment per block. At a 480×270 grid, one fullscreen-triangle draw is 130k fragments, not the ~2M of a device-resolution canvas.
- **texelFetch/gl_FragCoord at grid resolution**: the GLSL ES 3.00 spec (§7.2, fetched) defines `gl_FragCoord` in window coordinates; with the viewport set to the logical grid, `ivec2(gl_FragCoord.xy)` is the block's address, and the fetched spec's §8.8 `texelFetch` is the matching whole-texel read. MDN best practices separately warns `readPixels` and `getParameter` stall the pipeline (fetched) — confirming the loop's no-readback rule is about API round-trips, not about the render pattern itself.

## 4. Headless testing of the WebGL2 adapter

- **(a) headless-gl (native GL binding)**: it does now support WebGL2 — this corrects the older common knowledge that it was WebGL1-only. The README (github.com/stackgl/headless-gl, fetched) documents `createWebGL2Context: true` returning a `WebGL2RenderingContext`, built on ANGLE binaries downloaded at install, with prebuilt binaries for Node LTS (22, 24, 26) on Linux/macOS/Windows. The GitHub API release list (fetched) shows an active release cadence (v9.0.0-rc series through 2025, `angle-electron-43.8.6` published 2026-11-01). Caveats, all from the fetched README: its stated conformance suite is WebGL 1.0.3 only (617/620 passing); it makes no WebGL2 conformance claim; npm ≥12 requires install-script approval (`npm install-scripts approve gl`); and it renders through ANGLE's software path in Node, so it verifies GLSL correctness and GL semantics, not any real GPU's behaviour. What it can verify: that the kernel compiles, links, and produces visually-equivalent output under a real ES 3.0 implementation, inside plain `node --test`. What it cannot: device-GPU precision, driver quirks, or the browser's compositing/context path.
- **(b) transpiling the GLSL to JS**: the candidates do not hold up, checked directly. `glslx` (evanw/glslx, README fetched) is a type checker/formatter/minifier — it does not execute or transpile to JavaScript, and its README shows no ES 3.00 execution story. `glsl-transformer` (IrisShaders, README fetched) is a Java/ANTLR _syntax-transformation_ library, AGPL-licensed, whose own README says it "does not do semantic validation", "operates only on the syntactic level", and does not interpret `#version` — it cannot run a shader, and its AGPL would contaminate a Node test dependency besides. The stackgl `glsl-transpiler` (GLSL→JS) has no reachable README (raw file 404 on both default branches) and was documented for GLSL ES 1.00-era sources; no maintained ES 3.00 GLSL-to-JS execution engine was found. A transpile path also could not verify the actual GL contract at all — it would test a translation of the kernel, not the kernel. Reject this option; no primary source endorses it for equivalence testing because no such tool exists in working shape.
- **(c) headless Chromium via Playwright**: Chromium's own docs (chromium.googlesource.com, "Using Chromium with SwiftShader", fetched) state that SwiftShader is "an open-source high-performance implementation of the Vulkan and OpenGL ES graphics APIs which runs purely on the CPU" and that Chromium uses it as both the GLES driver and the WebGL fallback — headless Chromium without a GPU renders WebGL2 through a real browser stack, with the real context attributes, the real compositing path, and the real `webgl2` context creation the adapter ships behind. The repo already has a Playwright MCP server and a static `dist/` to drive. What it can verify: the full adapter path (context creation, static-texture upload, uniform upload, frame loop) and visual equivalence via a harness page that renders the same scene and frame state through both adapters and diffs buffers, with one `gl.readPixels` after the frame — the no-readback rule (ADR-0007, and MDN best practices on `readPixels` being a finish+round-trip) governs the animation loop, not a test's single verification read. What it cannot verify: cross-device GPU variance — SwiftShader is a CPU rasteriser, so it pins one implementation, which is precisely why the contract is visual equivalence, not bit-match (ADR-0007).

**Recommendation**: (c) Playwright against the built site as the primary — it is the only option that exercises the adapter's whole browser contract, it needs no new native dependency, and it aligns with the spec's visual-equivalence testing decision. (a) headless-gl is a viable supplement for fast, in-`node --test` kernel checks if the team accepts the native-binding install cost, now that it does WebGL2 — but its WebGL2 conformance is unclaimed, so treat it as a smoke/compile/equivalence harness, not an oracle. (b) is rejected: no maintained tool exists. Under ADR-0007 the GLSL kernel is never the oracle either way; the CPU core is, and both supplements diff against it.

## What could not be answered from primary sources

- Sprite caching for procedural pixel sprites painted into a raw pixel buffer: no primary source exists; MDN's 2D-context pre-rendering guidance is the nearest, and the exact keying/blit design is reasoning-from-the-repo (`paintBirds`' coverage/dither arithmetic).
- Whether every shipping mobile GPU implements fragment `highp` in hardware: no source answers this; the ES 3.00 profile makes it a conformance requirement, which is the strongest available statement.
- The precise restore procedure after `webglcontextrestored`: the spec defines the lost flag; the rebuild-via-resize answer is the repo's own.
- Shader source delivery (inline vs fetched): no source governs it; the inline recommendation is reasoning-from-the-repo.
- headless-gl's WebGL2 conformance: unclaimed by its own README; only its WebGL 1.0.3 conformance is documented.
